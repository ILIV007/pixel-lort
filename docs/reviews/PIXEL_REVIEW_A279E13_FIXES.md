## 1. The reproduced defects (RED on a279e13, both confirmed by the review's logs AND locally)

- **R1 — the swapped album usage binding healed `published`** (`healed_from_evidence`): the completeness evaluator (`evaluateAlbumDeliveryEvidence`, alsp1) verified that every plan ordinal was recorded to the configured destination and that every ordinal was BOUND in `media_usages` — but never verified WHICH asset each ordinal was bound to. A two-item album with both messages delivered correctly and the usages bound SWAPPED (ordinal 0 → asset 2, ordinal 1 → asset 1) satisfied the counts and was promoted `published` with wrong provenance. The review's probe observed `status=published, sends=0`; the fix must make the per-ordinal asset↔plan match part of the proof — fail-closed and atomic, the evidence preserved, auto-resend forbidden.
- **R2 — the recent-history window held the OLDEST rows**: `listRecentPublishedHistory` ordered `published_at ASC` and THEN applied `LIMIT 512`. After 512 publications the selection window was full of the oldest records and every NEW send fell outside it — the scheduler's cooldown/mix/layout policy consumed stale data (the review's 513-record probe: the newest record absent, `last=1700029790000` vs expected `1700029799000`).

## 2. The fixes

- **F1 (R1) — the binding-correctness proof.** The pure evaluator `evaluateAlbumDeliveryEvidence` (src/domain/media/album-send-plan.ts) now accepts two OPTIONAL binding views — the ledger's `boundUsages` (ordinal → media_asset_id) and the plan-resolved `expectedBindings` — and demands the EXACT per-ordinal pair equality: a swapped binding, a foreign asset, an extra/unknown ordinal, a duplicate or malformed row are all `usage_binding_mismatch`, never a proof. New verdict reason `usage_binding_mismatch`; the pre-a279 count-only contract is unchanged when the views are absent (pinned). The engine (`evaluateAlbumEvidenceAction` in the scheduler) now resolves the expected bindings from the ledger BEFORE the verdict — the SAME resolution the send path uses, so the rights gate (the d65d811 F3 gate) re-reads the durable echo AT the verification/heal moment too (a rights revocation after delivery dead-letters typed, zero sends). Verdict routing: complete → heal; `usage_binding_mismatch` → park `album_usage_mismatch` (records AND the wrong bindings stay EXACTLY as recorded — never rewritten, zero sends, never auto-resent); `unbound_usages` → reconcile the EXPECTED bindings then heal (the honest crash-after-delivery family — a mismatch can never reach this path, so the reconcile can never silently overwrite a wrong binding); `missing_ordinals`/`foreign_destination` → park `album_evidence_incomplete`. Phase A's failed-row reconcile consumes the SAME action.
- **F2 (R2) — the window selects the NEWEST records.** `listRecentPublishedHistory` (src/adapters/db/publication-outbox-store.ts) now orders `published_at DESC, id DESC` with the LIMIT — the deterministic tie-break at equal timestamps (id DESC selection, id ASC return) — and REVERSES the chosen window to oldest-first for the consumer (the trail's last entry IS the previous send; the consumer contract is byte-unchanged, the SELECTION is fixed). Honest bounded-read boundary: no index covers `published_at` (schema 6 — ZERO DDL), the engine sorts, the LIMIT keeps the returned window bounded exactly as before.
- **F3 (review item 3) — the machine never mints a publish clearance.** The review's `rightsStateFor` finding: an `official_api` origin or official/verified source metadata was promoted to a durable `official`/`attribution_required` echo — statuses the publication allowlist ACCEPTS, i.e. a republication permission invented from the source's name. Now: `rightsStateFor` feeds ONLY the mrp1 staging decision (an allow was always strictly `r2_temporary_only` — fetch + stage, never a publish grant; the scoping the d65d811 round documented stands), and `rightsStatusFor` returns `unknown` for EVERY machine-staged asset: the durable echo claims nothing the provenance does not carry. The publication gate (PUBLICATION_MEDIA_RIGHTS_V1) and the reuse predicate both refuse `unknown` — so machine-staged media is publishable/reusable ONLY after an explicit, evidence-backed owner action records an affirmative status (no such write surface exists — deliberately). The owner decision is filed as **OD-010** in docs/OPEN_DECISIONS.md (the rights-EVIDENCE model: scope/destination, expiry, attribution, the write surface, the upload path's own send gate). The consequences are pinned honestly: the reuse economy (zero-fetch replays) applies only to evidence-cleared rows — the media-73 economy/hash-reuse pins and the media-74 durable-echo pins are CORRECTED to the safe behavior (never weakened; every correction carries the review reference).
